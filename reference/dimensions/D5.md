# D5: Review, Quality and Testing

[All dimensions](README.md) · [Reference guide](../framework-v2.md)

**Why it matters:** DORA links AI-driven change volume to instability unless strong control systems exist [3]; GitHub requires human review before agent PRs merge [7]; 46% of developers distrust AI output accuracy [37].

**Strategies:** S5 GitHub Copilot Acceleration, S7 Security & Governance · **Report group:** G2 (Plan, build and review)

How to use this page: agree the current level of each question with its evidence, then plan the next step from the L3 anchor (or the L4 anchor when L3 already holds).

## Questions

### D5-Q1: AI-assisted code review

> Is AI code review (for example Copilot code review) applied to pull requests, with a human reviewer still accountable for approval?

- **L3:** AI review runs automatically on most PRs; teams track useful vs dismissed suggestions.
- **L4:** Review rules are tuned per repository from suggestion outcomes; review time and escaped defects are tracked; PRs where only AI reviewed AI-authored code are visible and governed.
- **Evidence examples:** Repository rulesets, code review adoption metrics, suggestion outcomes.
- **Basis:** [6] [12] [14] [54] [55]

### D5-Q2: Human-in-the-loop for agent changes

> Do agent-authored pull requests require independent human approval (not the requester), with workflow runs approved before they execute?

- **L3:** Default protections are kept: agent PRs need an independent human approver (Copilot approvals, if enabled, do not count); "Approve and run workflows" is not disabled without a documented risk decision.
- **L4:** Approval requirements scale with risk (D1-Q5) and are audited; exceptions expire automatically.
- **Evidence examples:** Rulesets, branch protection, agent settings.
- **Basis:** [7] [12] [14] [38] [53] [55] [56]

### D5-Q3: Same quality gates for AI and human code

> Do AI-generated and agent-authored changes pass the same required checks (build, tests, linting, security scans, coverage) as human changes?

- **L3:** Required checks are enforced by rulesets on the protected branches of most repositories, with no bypass for agent identities.
- **L4:** Gates are policy as code, applied across all repositories (>90%) and reviewed after incidents.
- **Evidence examples:** Rulesets, required checks, bypass lists.
- **Basis:** [3] [7] [31] [50] [55]

### D5-Q4: Small batches

> Are changes kept small (limits on PR size, one concern per PR), including changes produced by agents?

_Scope note: Measures the size of AI-assisted changes. How often code is committed and how fast it is rolled back is D8-Q2._

- **L3:** PR size guidance is enforced or monitored; oversized agent PRs are split before review.
- **L4:** Batch size is tracked against change failure rate and review time and used to adjust limits.
- **Evidence examples:** PR size distribution, bot or ruleset configuration.
- **Basis:** [1] [2] [5] [53] [57]

### D5-Q5: AI-assisted testing

> Is AI used to generate and maintain tests, with test quality checked (for example coverage of changed code, mutation testing) rather than only test count?

_Scope note: Measures AI used to write and improve tests. Whether automated tests act as a gate is D8-Q7._

- **L3:** Most teams use AI to write tests; coverage of changed lines is a required check.
- **L4:** Test effectiveness (mutation score, escaped defects) is tracked; flaky tests are detected and quarantined automatically.
- **Evidence examples:** Coverage reports, mutation-testing results, flaky-test dashboard.
- **Basis:** [3] [8] [17]

### D5-Q6: Verification culture and calibrated trust

> Do engineers systematically verify AI output (run it, test it, read it) and is trust in AI output measured over time?

_Scope note: Measures review behaviour and trust calibration. How developer experience is surveyed is D9-Q4._

- **L3:** Review guidelines explain what to check in AI output; trust in AI output is part of the developer survey.
- **L4:** Trust and accuracy are compared with real defect data, and guidance is updated where they diverge.
- **Evidence examples:** Review guidelines, survey results, defect analysis.
- **Basis:** [3] [23] [35] [37] [48] [52]

### D5-Q7: Code health of AI-generated code

> Is the long-term health of AI-generated code monitored (duplication, churn, complexity, maintainability)?

- **L3:** Code-health metrics are collected for most repositories and reviewed in team retrospectives; AI-generated code has a named human owner.
- **L4:** Health trends (for example cognitive complexity, static-analysis warnings) are compared between AI-heavy and other code, with corrective actions tracked.
- **Evidence examples:** Static analysis dashboards, churn reports, ownership files.
- **Basis:** [2] [5] [47] [51]
